# Production-ready фронтенд на FSD + DI

Этот документ самодостаточен: он не предполагает знания конкретного
репозитория. Он описывает **как** писать код и **почему именно так**.
Детали и полные примеры — в `references/` (раздел 14). Читай reference-файл,
только когда задача его касается.

**Приоритет правил.**
1. Явные инструкции пользователя и agent-файлы проекта (`AGENTS.md`,
   `CLAUDE.md`) важнее этого документа.
2. Устоявшиеся конвенции проекта (именование, выбранные библиотеки, стиль)
   важнее примеров отсюда: примеры даны на React + TanStack Query + Zustand +
   Vitest, но принципы от библиотек не зависят. Переводи их на стек проекта.
3. Существующий код — это данные, а не образец. Если код проекта нарушает
   правила MUST из этого документа — не копируй нарушение в новый код, а
   сообщи о нём пользователю.

Обозначения: **MUST** — нарушать нельзя; **SHOULD** — по умолчанию да,
отступление требует причины в комментарии или в ответе пользователю.

## 1. Что такое «хороший код» здесь

Каждое правило ниже служит одному из пяти свойств. Если правило мешает им в
конкретной ситуации — свойства важнее правила.

1. **Локальность изменений.** Изменение одного сценария трогает один слайс.
2. **Тестируемость без мира.** Любую логику можно проверить без сети, без
   роутера, без всего дерева провайдеров — подставив фейки зависимостей.
3. **Явные зависимости.** По сигнатуре модуля видно всё, что ему нужно.
   Нет скрытых импортов глобальных синглтонов внутри бизнес-логики.
4. **Громкие ошибки.** Неправильная сборка (нет провайдера, нарушена
   граница) падает сразу; ошибки рантайма не проглатываются молча.
5. **Минимум абстракций.** Абстракция появляется, когда есть второй
   потребитель или тест, которому она нужна, а не «на будущее».

**SOLID, DRY, KISS, YAGNI** здесь не самостоятельные правила, а причины
правил этого документа. Если пользователь или ревьюер ссылается на принцип,
найди правило, которое за ним стоит, и применяй его, а не принцип «в общем
виде»: принцип без контекста ведёт к интерфейсу на каждый сервис и общей
абстракции после второго похожего куска кода.

| Принцип | Правило здесь |
|---|---|
| YAGNI | Абстракция — при втором потребителе или тесте (п. 5 выше); правило выноса (раздел 3); нет слайсов «на будущее» |
| DRY | Для знаний, а не для кода: бизнес-правило — в одном месте. Похожий код дублируется до третьего случая (раздел 13) |
| KISS | Самая нижняя подходящая ступень DI (4.1); пропс раньше контекста (раздел 13) |
| SRP | Анатомия слайса и три уровня логики (раздел 5) |
| OCP | Композиция и слоты вместо булевых флагов (`references/conventions.md`, раздел 5) |
| ISP | Контракт минимален (C2) |
| DIP | Контракт объявляет потребитель в своих терминах (раздел 4) |

Принципы конфликтуют (DRY против YAGNI и KISS); конфликт разрешает раздел 13.
Отступление от правила — с причиной в коде или в ADR.

## 2. Слои и правило импорта

```text
app/       инициализация, провайдеры, роутинг, глобальные лейауты, реализации
           глобальных сервисов (toast, confirm, навигация, i18n, API-клиент)
pages/     экран целиком: композиция слайсов + логика, нужная только ему
widgets/   (не рекомендуется) переиспользуемые крупные блоки; новые не создавать,
           если в проекте их нет — композиция живёт в pages
features/  переиспользуемые пользовательские сценарии (глагол: create-task,
           move-card, sign-in, edit-profile)
entities/  переиспользуемые бизнес-сущности (существительное: task, user,
           board): типы, запросы, доменные правила, отображение сущности
shared/    инфраструктура без бизнес-правил: ui-кит, api-клиент, lib, config
```

**MUST:**
- **Импорт только вниз:** модуль импортирует только из слоёв строго ниже.
  `app` и `shared` — без слайсов; их сегменты могут импортировать друг друга.
- **Нет cross-import** между слайсами одного слоя (`features/a` ↛
  `features/b`, `entities/a` ↛ `entities/b`). Как обойтись — раздел 4.
- **Public API:** снаружи слайса импортируется только его `index.ts`
  (и, опционально, `testing.ts` — только из тестов). Глубокие импорты
  (`@/features/x/model/store`) запрещены.
- **В `shared` нет бизнес-правил.** Бизнес-правило — то, что продукт
  требует от своих данных («владелец может передать доску», «скидка не
  больше 30%»). UI-логика (автокомплит), CRUD-обвязка и бренд — можно.
- Границы проверяются линтером (`eslint-plugin-boundaries` или `steiger`),
  а не только договорённостью. Конфиг — `references/conventions.md`.

## 3. Куда положить код

Идём сверху вниз, берём первый подходящий ответ:

1. Инфраструктура без бизнес-правил (кнопка, модалка, http-клиент, форматтер
   дат, обёртка над localStorage)? → `shared/{ui,api,lib,config}`
2. Инициализация приложения, глобальный провайдер, роутинг, интерцептор,
   лейаут всего приложения? → `app/`
3. Нужно только одной странице? → `pages/<page>/` — **даже если это сложная
   логика.** Дублирование между страницами допустимо.
4. Пользовательский сценарий, нужный в 2+ местах прямо сейчас? →
   `features/<verb-noun>/`
5. Данные/правила/отображение бизнес-сущности, нужные в 2+ слайсах? →
   `entities/<noun>/`

**Правило выноса (SHOULD).** Выноси код из `pages` ниже, только если
одновременно: (а) он реально используется в нескольких местах сейчас;
(б) у него своя причина меняться, не зависящая от одного потребителя;
(в) у будущего слайса узкая, называемая одним словом ответственность.

**Слишком мелкие сущности — признак ошибки.** Если `entities/a` постоянно
нужен `entities/b`, вероятно, это одна сущность. Объедини.

## 4. Инверсия зависимостей — ядро архитектуры

Правило импорта неизбежно сталкивается с реальностью: фиче «доска» нужно
создавать задачи и открывать диалог редактирования задачи из другой фичи.
Cross-import запрещён. Выход — **инверсия**: модуль объявляет, *что* ему
нужно, а *кто* это даст, решает слой выше, который видит обе стороны.

### 4.1. Лестница: бери самую нижнюю подходящую ступень

| # | Механизм | Когда | Пример |
|---|---|---|---|
| 1 | **Пропсы / аргументы / колбэки** | Зависимость нужна одному компоненту/функции на 1–2 уровня вниз | `<SignInForm onSuccess={() => navigate("/")} />`, `canAssign(user)` в пропсе |
| 2 | **Композиция: children / render props / слоты** | Модулю нужно *показать* чужой UI внутри себя | `renderCardActions={(card) => <EditTaskButton id={card.id} />}` |
| 3 | **Контракт `deps` + strict context** | Зависимость нужна глубоко в дереве или многим компонентам/хукам слайса | `TaskBoardDepsProvider value={{ createCard, editCard }}` |
| 4 | **Фабрика с зависимостями** | Нереактивная логика (стор, сервис, use-case), которую надо тестировать без React | `createBoardStore(initial, getDeps)` |

Ступени комбинируются: на практике контекст (3) поставляет `deps` в
провайдер, который создаёт стор фабрикой (4).

### 4.2. Правила контрактов (MUST)

- **C1. Контракт объявляет потребитель и в своих терминах.** Фича доски
  говорит о `BoardCard`, а не о `Task`. Перевод `Task → BoardCard` —
  работа адаптера в слое выше.
- **C2. Контракт минимален:** только реально используемые функции и
  значения. Не передавай «весь стор» или «весь API-клиент».
- **C3. Асинхронные операции возвращают `Promise`.** Отмена пользователем —
  это значение (`null` / `false`), а не исключение. Исключение — это ошибка.
- **C4. Связывание делает самый нижний слой, видящий обе стороны** —
  обычно `pages`, для глобальных сервисов — `app`.
- **C5. Нет провайдера — громкая ошибка** (strict context), никаких
  тихих `null` и дефолтных заглушек в проде.
- **C6. Для каждого контракта есть фейк** для тестов
  (`createFake<Name>Deps(overrides)`), экспортируемый из `testing.ts` слайса.
- **C7. DI — не для всего.** Импорт вниз по слоям нормален и не требует DI:
  `shared/ui`, утилиты, типы, запросы сущности импортируются напрямую.
  Инвертируй, когда зависимость: (а) из того же или вышестоящего слоя;
  (б) должна иметь разные реализации у разных потребителей; (в) является
  побочным эффектом (сеть, навигация, диалог, тост, время, генерация id),
  который надо подменять в тестах **нереактивной** логики.

### 4.3. Минимальный пример (контракт + фабрика + адаптер)

```ts
// features/task-board/model/deps.ts — контракт объявляет потребитель, в своих терминах
export type TaskBoardDeps = {
  createCard: (input: { title: string }) => Promise<BoardCard>;
  /** Открывает редактор. null — пользователь отменил. */
  editCard: (cardId: string) => Promise<BoardCard | null>;
  saveBoard: (board: Board) => Promise<void>;
};

// features/task-board/model/board-store.ts — стор не импортирует api, он получает deps
export function createBoardStore(initial: Board, getDeps: () => TaskBoardDeps) {
  return createStore<BoardState>()((set, get) => ({
    board: initial,
    addCard: async (columnId, title) => {
      const card = await getDeps().createCard({ title });
      const next = addCard(get().board, columnId, card); // чистая функция из model/board.ts
      set({ board: next });
      await getDeps().saveBoard(next);                    // (откат при ошибке — см. reference)
    },
    // ...
  }));
}
```

```tsx
// pages/board/model/use-task-board-adapter.ts — только здесь видны обе стороны
export function useTaskBoardAdapter(board: Board): TaskBoardDeps {
  const createTask = useCreateTask();        // entities/task
  const openEditTask = useEditTaskDialog();  // features/edit-task
  const saveBoard = useSaveBoard();          // entities/board
  return {
    createCard: async ({ title }) => toBoardCard(await createTask({ title, boardId: board.id })),
    editCard: async (id) => {
      const task = await openEditTask(id, { canAssignUser: (userId) => isBoardMember(board, userId) });
      return task ? toBoardCard(task) : null;
    },
    saveBoard: (next) => saveBoard(toBoardDto(next)),
  };
}

// pages/board/ui/board-screen.tsx (рендерится с key={board.id})
function BoardScreen({ board }: { board: Board }) {
  const deps = useTaskBoardAdapter(board);
  return (
    <TaskBoardProvider initialBoard={toTaskBoard(board)} deps={deps}>
      <TaskBoard />
    </TaskBoardProvider>
  );
}
```

Полный разбор (все четыре ступени, фабрика стора, глобальные сервисы
confirm/toast/navigate, promise-диалоги, события между слайсами, ловушки
вроде «устаревших deps») — **`references/dependency-injection.md`**.
Прочитай его перед любой задачей, где один слайс должен использовать другой.

## 5. Анатомия слайса

```text
features/task-board/
├── index.ts            # MUST. Public API: явные именованные экспорты
├── testing.ts          # SHOULD при наличии deps: фейки и билдеры для тестов
├── model/
│   ├── deps.ts         # контракт внешних зависимостей + strict context
│   ├── board.ts        # доменные типы и ЧИСТЫЕ функции (moveCard, canDrop…)
│   ├── board.test.ts
│   ├── board-store.ts  # фабрика стора: оркестрация, вызывает board.ts и deps
│   ├── board-store.test.ts
│   └── use-*.ts        # React-хуки слайса
├── api/                # запросы, которые нужны только этому слайсу
├── ui/                 # компоненты; *.test.tsx рядом
├── lib/                # внутренние утилиты слайса
└── i18n.ts             # тексты слайса (или ui/i18n.ts)
```

- Сегменты создаются **по необходимости**, пустых папок нет.
- Имена файлов — по предметной области (`board-store.ts`, `card-title.tsx`),
  а не по технической роли (`helpers.ts`, `utils.ts`, `types.ts` на весь
  слайс — плохо).
- Тест лежит рядом с тестируемым файлом.

### Три уровня логики внутри слайса

```text
ui/      ─►  model/use-*.ts / store  ─►  model/<domain>.ts (чистые функции)
 рендер,      оркестрация: что вызвать,     правила и вычисления:
 события      в каком порядке, через deps   данные на вход → данные на выход
```

Чем ниже уровень, тем меньше у него зависимостей. Чистые функции не знают
ни про React, ни про сеть, ни про deps — это самый ценный и самый дешёвый в
тестировании код. **SHOULD: любое нетривиальное правило или преобразование
данных — чистая функция с unit-тестом.**

## 6. Состояние и данные

Сначала классифицируй состояние — от класса зависит инструмент:

| Класс | Инструмент | Где |
|---|---|---|
| Серверное (данные бэкенда) | библиотека кэша запросов (TanStack Query, RTK Query, SWR) | фабрики запросов в `entities/<x>/api` или `shared/api` |
| URL (фильтры, пагинация, выбранная вкладка) | роутер / search params | `pages` |
| Форма | библиотека форм | слайс, где живёт форма |
| Локальное UI | `useState` / `useReducer` | компонент |
| Клиентское, общее для поддерева | стор-фабрика + context, **экземпляр на провайдер** | `model/` слайса |
| Глобальное клиентское (тема, язык) | стор в `app` или `entities` | инициализация в `app` |
| Производное | вычисляй, не храни | селектор / `useMemo` / чистая функция |

**MUST:** нет синглтон-сторов на уровне модуля для данных, зависящих от
пользователя/страницы; DTO бэкенда не протекают в UI без маппинга на
границе API; каждый асинхронный UI обрабатывает состояния loading / error /
empty / success; оптимистичное обновление всегда умеет откатиться.

Подробно: **`references/state-and-data.md`**.

## 7. Ошибки и async (MUST)

- Никаких пустых `catch {}` / `.catch(() => {})` / `.catch()` и `catch`,
  возвращающих «пустые данные». Ошибка либо обработана осмысленно
  (пользователь увидел сообщение, состояние откатилось), либо проброшена.
- Решение «как показать ошибку» принимает слой, владеющий UX (хук фичи или
  страница), а не стор и не доменная функция: они бросают / реджектят.
- `throw new Error("…")` — всегда с сообщением и, если есть, `{ cause }`.
- Каждый `Promise` либо `await`-ится, либо явно помечен `void` с
  обработкой ошибки внутри.
- Код, который читает `error.response.status`, сначала проверяет, что
  `response` вообще есть (сетевые ошибки и отмены его не имеют).
- Вид ошибки определяется по коду (статус, `extensions.code`, `code` в
  теле), а не по тексту сообщения. В логах нет персональных данных и
  токенов.
- На уровне страницы — error boundary; на уровне приложения — глобальный
  обработчик 401/403 в API-клиенте, зарегистрированный один раз с очисткой.

Подробно: **`references/conventions.md`**, раздел «Ошибки».

## 8. Тестирование

Цель — уверенность при изменениях, а не процент покрытия.

| Что | Как | Обязательность |
|---|---|---|
| Чистые доменные функции | unit, без моков | MUST для нетривиальной логики |
| Стор / use-case (фабрика) | unit с фейковыми deps | MUST, если есть deps |
| Компонент / хук слайса | Testing Library, провайдер с фейковыми deps | SHOULD для сценариев пользователя |
| Хуки с серверными данными | Testing Library + MSW + свежий QueryClient | SHOULD |
| Страница / сборка | интеграционный тест с MSW | SHOULD для ключевых экранов |
| Критические пути | e2e (Playwright) | по договорённости с проектом |

**MUST:** тестируй поведение через public API слайса; подменяй зависимости
через DI, а не `vi.mock` собственных модулей (`vi.mock` — только для
сторонних модулей, которые нельзя внедрить). Подробно и с примерами:
**`references/testing.md`**.

## 9. Конвенции кода (кратко)

- TypeScript `strict`. Без `any`, `@ts-ignore`, `as unknown as`.
  `@ts-expect-error` — только с комментарием-причиной.
- Состояния — discriminated unions; `switch` — с exhaustive-проверкой.
- Файлы и папки — `kebab-case`. Хук (`use-*`) — только функция, которая
  вызывает другие хуки; чистая функция не называется `useX`.
- **Имена — это API. Опечатки в экспортируемых именах недопустимы.**
- Ни одной видимой пользователю строки в коде вне i18n-модуля. Стор и
  доменные функции текстов не содержат.
- Ключи списков — стабильные id, никогда не индекс, если список
  фильтруется, сортируется или переставляется.
- Правило доступа описано **в одном месте** (чистая функция или ability в
  сущности); UI только скрывает элементы, сервер — источник истины.
- URL, ключи, флаги — из типизированного конфига (`shared/config`), не
  захардкожены.
- Интерактивные элементы — семантические (`button`, `a`, `label`); у
  кнопок-иконок есть `aria-label`; модалка управляет фокусом.

Подробно: **`references/conventions.md`**.

## 10. Главные анти-паттерны

1. Cross-import между слайсами одного слоя «потому что быстрее».
2. Скрытая зависимость: фабрика стора импортирует `api`/роутер/синглтон
   внутри себя, а не получает через deps.
3. Контракт `deps` в терминах поставщика (`Task` внутри фичи доски).
4. Один побочный эффект в двух местах (confirm и в хуке, и в сторе).
5. Тихое проглатывание ошибок; оптимистичное обновление без отката.
6. Индекс отфильтрованного списка используется как идентификатор.
7. Селектор возвращает новый объект/массив на каждый вызов.
8. Одно бизнес-правило продублировано в нескольких слайсах.
9. DI ради DI: контекст для того, что можно передать пропсом.
10. Преждевременный вынос в `entities`/`features` с одним потребителем.

Каждый — с плохим и хорошим примером: **`references/anti-patterns.md`**.

## 11. Порядок работы над задачей

1. **Разберись в стеке и конвенциях проекта:** библиотеки, линтер границ,
   существующие утилиты (`createStrictContext`, API-клиент, i18n, диалоги).
   Используй существующее; не плоди вторую реализацию того же.
2. **Размести код** по разделу 3. Если нужна связь между слайсами —
   выбери ступень по разделу 4.1.
3. **Спроектируй контракты** до реализации: публичный API слайса
   (`index.ts`), контракт `deps`, типы входа/выхода.
4. **Чистая логика + её тесты.**
5. **Оркестрация** (стор / хуки) через deps + тесты с фейками.
6. **UI**: получает данные из хуков/пропсов, отдаёт события наверх.
7. **Сборка** в странице: адаптеры deps, провайдеры, композиция.
8. **Проверка** по Definition of Done (раздел 12). Запусти typecheck,
   линтер и тесты сам — не утверждай, что они проходят, не запустив их.

## 12. Definition of Done

- [ ] `tsc --noEmit`, линтер (включая границы слоёв) и тесты проходят.
- [ ] Нет импортов вверх, cross-import и глубоких импортов мимо `index.ts`.
- [ ] Новые внешние зависимости слайса выражены контрактом (`deps`/пропсы),
      а не скрытыми импортами в нереактивной логике.
- [ ] Нетривиальная логика — в чистых функциях и покрыта unit-тестами;
      для контрактов есть фейки.
- [ ] Все async-пути обрабатывают ошибку; UI показывает loading / error /
      empty; оптимистичные обновления откатываются.
- [ ] Нет захардкоженных пользовательских строк, URL, магических значений.
- [ ] Нет `any`, `@ts-ignore`, пустых `catch`, `console.log`, мёртвого кода.
- [ ] Имена осмысленные, без опечаток; public API минимален.
- [ ] Ничего не создано «на будущее»: нет пустых сегментов, слайсов с
      одним потребителем, неиспользуемых экспортов.

## 13. Когда сомневаешься

- Между «вынести» и «оставить на странице» — оставь на странице.
- Между «контекст» и «пропс» — пропс.
- Между «новая абстракция» и «немного дублирования» — дублирование,
  пока не появится третий случай.
- Между «тихо обработать» и «упасть громко» — громко.
- Между «сделать как в соседнем файле» и «сделать по этому документу» —
  по документу, и сообщи о расхождении.
